# Overview
Integrate **Google Gemini 2.5 Flash Image API** as the primary text-to-image provider for the Image Generator Chat App. This phase connects user messages to image generation jobs, tracks job status asynchronously, and stores generated image results. This is the core feature that transforms the chat app into an image generation platform.

---

# Goals (MVP)
- Configure and authenticate with Google Gemini 2.5 Flash API via Vertex AI
- Create image generation jobs when users send messages with text prompts
- Track job lifecycle (queued → processing → succeeded/failed)
- Store generated images in the database with proper relationships
- Return image URLs to users via the existing message structure
- Handle async job processing (jobs continue even if user leaves thread)
- Implement robust error handling for API failures
- Calculate and track token usage for billing/monitoring

---

# Non-Goals (Explicitly Skipped)
- Multiple provider support (use Gemini 2.5 Flash only)
- Provider switching UI or routing logic
- Advanced image parameters (use defaults for MVP)
- Image editing features (img2img, inpaint, upscale, variation)
- Real-time websocket updates (polling is acceptable)
- Queue system with Redis/Bull (simple async is fine)
- Retry logic for failed jobs (manual retry only)

---

# Data Model Integration

## Providers Table
Create a default Gemini provider record on first boot:
```js
// Pseudo-code for seed/migration
const provider = await db.insert(providers).values({
  name: 'gemini-2.5-flash',
  config: {
    model: 'gemini-2.5-flash',
    endpoint: 'https://us-central1-aiplatform.googleapis.com/v1',
    description: 'Google Gemini 2.5 Flash - Fast text-to-image generation'
  }
}).returning();
```

## Jobs Table Workflow
1. **User creates message** (role=user, content=prompt)
2. **System creates job** linked to that message:
   - `message_id`: UUID of user message
   - `provider_id`: UUID of Gemini provider
   - `job_type`: 'text2img'
   - `status`: 'queued'
   - `parameters`: JSON with prompt, width, height
3. **System creates assistant message** (role=assistant, content='', status='processing')
4. **Job processes asynchronously**:
   - Update job `status` to 'processing'
   - Call Gemini API
   - On success:
     - Update job `status` to 'succeeded'
     - Insert into `images` table with URL and metadata
     - Update assistant message `status` to 'succeeded'
     - Update assistant message `content` with image description
   - On failure:
     - Update job `status` to 'failed'
     - Update assistant message `status` to 'failed'
     - Update assistant message `content` with error message

# Job Processing Flow

## Synchronous Flow (API Request)
```
User → POST /api/threads/:threadId/messages
  ↓
1. Create user message (role=user, content=prompt)
  ↓
2. Get default provider (Gemini)
  ↓
3. Create job (status=queued, linked to message)
  ↓
4. Create assistant message (role=assistant, status=processing)
  ↓
5. Trigger async job processing (do not await)
  ↓
6. Return 201 response immediately
```

## Asynchronous Flow (Background Processing)
```
processJob(jobId) triggered
  ↓
1. Update job status to 'processing'
  ↓
2. Call gemini.service.generateImage(prompt)
  ↓
3. Gemini API processes (may take 10-60 seconds)
  ↓
4. Receive response with imageUrl and metadata
  ↓
5. Insert image record into images table
  ↓
6. Update job status to 'succeeded'
  ↓
7. Update assistant message:
   - status = 'succeeded'
   - content = "Generated image for: {prompt}"
  ↓
Done (user sees result on next poll/refresh)
```

# Error Handling Patterns

## Gemini API Errors
```js
try {
  const result = await generateImage(prompt);
} catch (error) {
  // Map to standard error format
  if (get(error, 'response.status') === 429) {
    // Rate limit
    return errorResponse('Rate limit exceeded, please try again later', 429);
  }
  if (get(error, 'response.status') === 400) {
    // Invalid prompt
    return errorResponse('Invalid prompt provided', 400);
  }
  // Generic error
  return errorResponse('Image generation failed', 500);
}
```

## Job Processing Errors
```js
async function processJob(jobId) {
  try {
    // ... processing logic
  } catch (error) {
    // Update job and message to failed state
    await updateJobStatus(jobId, 'failed', {
      error: get(error, 'message', 'Unknown error')
    });
    
    await updateMessage(assistantMessageId, {
      status: 'failed',
      content: `Failed to generate image: ${get(error, 'message')}`
    });
    
    // Log error for monitoring
    console.error('[Job Processing Error]', {
      jobId,
      error: get(error, 'message'),
      stack: get(error, 'stack')
    });
  }
}
```

# Database Queries (Drizzle ORM)

## Create Job
```js
import { jobs } from '../db/schema.js';
import { db } from '../db/drizzle.js';

const job = await db.insert(jobs).values({
  messageId: messageUuid,
  providerId: providerUuid,
  jobType: 'text2img',
  status: 'queued',
  parameters: {
    prompt,
    width: 1024,
    height: 1024
  }
}).returning();
```

## Update Job Status
```js
import { eq } from 'drizzle-orm';

await db.update(jobs)
  .set({ 
    status: 'succeeded',
    updatedAt: new Date()
  })
  .where(eq(jobs.id, jobId));
```

## Get Job with Images
```js
import { jobs, images } from '../db/schema.js';
import { eq } from 'drizzle-orm';

const jobWithImages = await db
  .select()
  .from(jobs)
  .leftJoin(images, eq(jobs.id, images.jobId))
  .where(eq(jobs.id, jobId));
```

# Security Considerations

1. **API Keys Protection:**
   - NEVER expose service account JSON in client
   - NEVER commit credentials to git
   - Use environment variables only
   - Restrict service account permissions to minimum required

2. **Prompt Validation:**
   - Sanitize user input
   - Enforce max prompt length (1000 chars)
   - Filter prohibited content (optional, basic for MVP)

3. **Rate Limiting:**
   - Implement per-user request limits
   - Track API quotas
   - Handle 429 errors gracefully

4. **Authorization:**
   - Verify user owns thread before creating job
   - Enforce ownership on job status checks
